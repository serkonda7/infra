rig — design document

A single-binary tool that converges a Linux machine — packages, system config, services, users and dotfiles — to a state described in typed TypeScript. Ansible's “just run it” ergonomics, Nix's “what's declared is what exists” guarantee, without a new language.

Bun ≥ 1.2TypeScriptCachyOS (primary)Debian (server)Draft · 2026-10-13

Goals & non-goals

Declarative & convergent

Config describes desired state. Running rig apply twice changes nothing the second time.

Removal is first-class

Delete a line from config → the file, unit or package it created goes away. This is the main thing Ansible lacks.

Plan before apply

Every run computes a diff (Terraform-style) that you can review. Dry-run is the default mental model.

Just TypeScript

Modules are functions. Conditionals, loops and reuse are plain TS with full type-checking and editor completion.

Zero runtime deps on targets

Ships as one bun build --compile binary. Remote hosts need only SSH and sudo.

Arch-first, Debian-capable

pacman + AUR (paru), CachyOS repos, btrfs/snapper snapshots. apt as a second backend.

Non-goals

  • Hermetic builds / reproducible store. We use the distro package manager; we don't pin every package to a hash like Nix.
  • Fleet scale. Target is 1–10 machines owned by one person. No inventory database, no parallel push to 500 hosts.
  • Windows / macOS. Linux only. (Dotfile linking would work on macOS, but it is not tested.)
  • Provisioning infrastructure. No VMs, cloud, DNS. Use Terraform/OpenTofu for that.

Core concepts

ConceptWhat it is
HostA named machine definition: target OS, connection info, and the list of modules applied to it.
FactsRead-only data gathered from the target before evaluation: distro, arch, CPU level (x86-64-v3/v4), GPU vendor, hostname, filesystem type of /, users, init system.
ModuleA function (ctx) => void that declares resources. Can take options and include other modules. The unit of reuse.
ResourceOne managed thing with a stable ID: pkg:pacman:neovim, file:/etc/sysctl.d/99-rig.conf, unit:user:syncthing.service. Knows how to read, diff, apply and destroy itself.
GraphResources plus edges (explicit after, implicit e.g. file → parent dir, unit → package). Topologically sorted for apply.
PlanGraph + current state → list of actions (create / update / destroy / noop). Serializable, printable, approvable.
GenerationRecord of the resource set successfully applied in a run. Stored locally; used for pruning and rollback.
TriggerAnsible-style handler: “if any of these resources changed, run this action once at the end” (e.g. restart a service, mkinitcpio -P, limine-update).

Configuration API

Entry point

// rig.config.ts
import { defineConfig } from "rig";

export default defineConfig({
  hosts: {
    zephyr: () => import("./hosts/zephyr"),
    atlas:  () => import("./hosts/atlas"),
    vault:  () => import("./hosts/vault"),
  },
  defaults: { user: "john", snapshots: "snapper" },
});

rig apply with no argument selects the host whose name matches hostname.

Host

// hosts/zephyr.ts
import { host } from "rig";
import { base } from "../modules/base";
import { kde } from "../modules/desktop/kde";
import { gaming } from "../modules/desktop/gaming";
import { dev } from "../modules/dev";

export default host({
  os: "arch",                        // family; CachyOS detected via facts
  packages: { mode: "exact" },       // prune undeclared explicit packages
  modules: [
    base,
    kde({ wayland: true }),
    gaming({ steam: true, gamescope: true }),
    dev,
  ],
});

Module

A module receives a context with resource builders and facts. Builders register resources; they don't execute anything. This keeps evaluation pure and makes plan cheap.

// modules/dev.ts
import { module } from "rig";

export const dev = module("dev", ({ pkg, link, file, unit, facts, user, tmpl }) => {
  pkg(["git", "neovim", "ripgrep", "fd", "bun", "docker", "docker-buildx"]);
  pkg.aur(["visual-studio-code-bin"]);

  link("~/.config/nvim", "dotfiles/nvim");              // whole-dir symlink
  file("~/.gitconfig", tmpl`
[user]
  name = John
  email = ${user.email}
[core]
  editor = nvim
`);

  unit("docker.service", { enabled: true, started: true });
  user.groups(["docker"]);

  if (facts.gpu.vendor === "nvidia") {
    pkg(["nvidia-container-toolkit"]);
  }
});

Module options with types

export const gaming = module("gaming", (ctx, opts: { steam?: boolean; gamescope?: boolean } = {}) => {
  ctx.pkg(["cachyos-gaming-meta"]);
  if (opts.steam) ctx.pkg(["steam"]);
  if (opts.gamescope) ctx.pkg(["gamescope"]);
  ctx.sysctl({ "vm.max_map_count": 2147483642 });
});

module(name, fn) returns a callable that is also usable bare (dev vs dev({...})). Each module invocation is tagged in resource provenance, so rig why pkg:pacman:steam can answer “declared by gaming (hosts/zephyr.ts:12)”.

Cross-distro package names

pkg([
  "git",                                              // same name everywhere
  { arch: "base-devel", debian: "build-essential" },
  { arch: "fd",         debian: "fd-find" },
]);

A small built-in alias table covers common mismatches (fd, bat, openssh/openssh-server…). Unknown names on the wrong distro are a plan-time error, not a runtime surprise.

Escape hatch

exec("rustup default stable", {
  unless: "rustup default | grep -q stable",     // guard → idempotent
  after: ["pkg:pacman:rustup"],
  asUser: true,
});

Shell commands without a guard (unless / creates / onChange) emit a lint warning: they'd run on every apply.

Execution engine

1. LoadBun imports config TS directly — no build step
→
2. FactsProbe target (cached per run)
→
3. EvaluateRun modules → resource set + edges
→
4. ValidateDuplicate IDs, conflicts, cycles, unknown pkgs
→
5. PlanRead current state, diff vs desired + previous generation
→
6. ApplySnapshot → topo-order apply → triggers
→
7. CommitWrite new generation

Evaluation rules

  • Duplicate IDs are merged if their specs are equal (two modules both want git), otherwise a conflict error that names both declaration sites.
  • Mergeable resources (pkg, user.groups, sysctl) union their values.
  • Implicit edges: a file depends on its parent dir; a unit depends on any package that ships it (resolved via pacman -Qo/dpkg -S at plan time); AUR packages depend on base-devel + paru.

Apply semantics

  • Batching. All pacman installs in a single transaction; all removals in one. Resource types can implement applyBatch.
  • Parallelism. Independent resources at the same topo level run concurrently (bounded); package ops are serialized (pacman lock).
  • Failure. On error, stop dependents, continue independent branches, record a partial generation. Next run picks up from real state — no special recovery needed because everything re-reads state.
  • Triggers run once at the end, in declaration order, only if a subscribed resource changed.

State, pruning & rollback

Unlike Terraform, live state is always re-read — the state file is not a source of truth for what exists. It only records what rig owns, so it knows what it may remove.

// /var/lib/rig/generations/42.json   (system)   ~/.local/state/rig/… (user)
{
  "id": 42, "at": "2026-10-13T10:12:00Z", "commit": "a1b2c3d", "status": "ok",
  "snapshot": "snapper:#318",
  "resources": {
    "file:/etc/sysctl.d/90-rig.conf": { "hash": "xxh3:…", "backup": "objects/9f…" },
    "pkg:pacman:steam": {},
    "link:/home/john/.config/nvim": { "target": "/home/john/infra/dotfiles/nvim" }
  }
}

Pruning

destroy set = previous generation − current desired set. Each removed resource's destroy() is called. Safety rules:

  • Files are only deleted if their current hash equals what rig last wrote. If a user edited it, rig refuses and reports drift (--force overrides).
  • Pre-existing files that rig overwrote on first apply are backed up in a content-addressed object store; destroying the resource restores the original instead of deleting.
  • Users, groups and data directories are never pruned unless the resource opts in (prune: true).

Rollback

  • Config-level: rig rollback 41 re-applies generation 41's resource set from the recorded git commit (checked out to a temp worktree).
  • System-level: on btrfs (CachyOS default) rig takes a snapper pre/post pair around each apply touching system resources, so a broken boot can be rolled back from the Limine snapshot menu. Configurable: snapshots: "snapper" | "btrfs" | "none".

Arch / CachyOS specifics

  • Respect CachyOS optimized repos (cachyos-v3, cachyos-v4, cachyos-znver4); repo() can manage pacman.conf ordering. A fact facts.cpu.level lets modules pick.
  • .pacnew files: plan warns when a managed file has a pending .pacnew sibling.
  • AUR builds run as the unprivileged user via paru --noconfirm --skipreview; rig bootstraps paru from the CachyOS repo if absent.
  • Kernel / initramfs: packages matching linux-cachyos* or *-dkms automatically subscribe to the bootloader trigger.
  • rig apply --upgrade does pacman -Syu first (never partial upgrades: installs always use the synced db from that run).

Debian specifics

  • DEBIAN_FRONTEND=noninteractive, apt-get -o Dpkg::Options::=--force-confold; config files we own are written after install anyway.
  • “Explicit” = apt-mark showmanual minus the installer's priority:required/important set.
  • Unattended upgrades configured by a stock module, not by rig core.

Dotfiles

Dotfiles are just file/link resources targeting $HOME, but they get extra tooling because they change constantly and are often edited in place.

Three strategies

StrategyHowWhen
linkSymlink into the repo. Edits in place go straight into git.Default. nvim, fish, kitty, anything not machine-specific.
file + tmplRendered from a TS tagged template with facts/secrets. Written as a real file.Per-host values, secrets, apps that hate symlinks.
copyCopied once; drift is reported but rig only overwrites with --force.Apps that rewrite their own config (KDE rc files, some Electron apps).

Bulk linking

// link every entry under dotfiles/home/ to ~, mirroring structure (like GNU stow)
link.tree("dotfiles/home", "~", { ignore: ["**/*.local"], granularity: "file" });

granularity: "dir" links top-level directories (fewer links, but the app's runtime files land in the repo); "file" links leaves (safer; default).

Workflow commands

  • rig adopt ~/.config/foo [--module dev] — moves the file into dotfiles/, replaces it with a link, appends a link() call to the module.
  • rig diff — for file/copy resources, shows live vs. desired (useful after an app rewrote its config).
  • rig pull ~/.config/foo — copies the live version back into the repo for copy resources.
  • rig dot — fast path: only home-scoped resources, no sudo, no facts beyond user-level. Runs in <200 ms so it can sit in a git hook.

Privilege model

rig always runs as your user. System-scoped resources go through a privileged helper:

rig (user)  ──spawn──▶  sudo rig __helper   # one password prompt per run
     │                         │
     └──── NDJSON RPC over stdin/stdout ────┘
           { op: "write", path, mode, owner, contentB64 }
           { op: "exec", argv, env }
           { op: "read", path } …
  • The helper is the same binary, exposing a small fixed op set — it never evaluates config. This keeps the root-side surface minimal and auditable.
  • Each resource declares scope: "user" | "system"; plan needs root only to read root-only files (helper started lazily).
  • rig dot and user-only plans never invoke sudo.
  • AUR builds explicitly run in the user process (makepkg refuses root).

Remote hosts (Debian server)

Push model over SSH, agentless. Evaluation happens on the target so facts are local and file reads are fast.

  1. Locally: bun build --compile --target=bun-linux-x64 (or -arm64) rig → cached binary, keyed by rig version.
  2. Bundle config: bun build the host's entry into a single JS file + tar of referenced dotfiles/ paths (tracked via the asset graph during evaluation). Secrets are decrypted locally and sent in-band, never written to remote disk unencrypted except as the final target file.
  3. SSH (single multiplexed connection, ControlMaster): upload binary to ~/.cache/rig/bin/<hash> if missing, stream bundle via stdin.
  4. Remote runs rig apply --bundle - --events ndjson; local CLI renders the event stream identically to a local run, including the interactive plan confirmation.
// hosts/vault.ts
export default host({
  os: "debian",
  connect: { ssh: "john@vault.lan", port: 22, sudo: "password" },
  modules: [base, hardening, caddy({ sites: ["git.example.com"] })],
});
Lockout safetyResources that can sever the connection (sshd_config, firewall, network) are applied last and wrapped in a dead-man's switch: rig schedules a systemd-run --on-active=120 revert, then cancels it after a fresh SSH connection succeeds.

Secrets

  • Format: age files in secrets/, encrypted to your SSH ed25519 key(s) and each host's SSH host key (like agenix). Decrypted with a pure-TS age implementation (age-encryption npm package) — no external binary.
  • API: secret("vault.env") returns an opaque Secret value. It can be interpolated into tmpl or passed as file content, but String(secret) throws — prevents accidental logging.
  • Plan output redacts secret-bearing diffs: ~ /etc/caddy/env (content changed, secret).
  • CLI: rig secret edit vault.env (decrypt → $EDITOR → re-encrypt), rig secret rekey after adding a host.
  • Written files with secrets default to mode 0600.

Fresh machine bootstrap

curl -fsSL https://github.com/<you>/rig/releases/latest/download/rig-linux-x64 -o /tmp/rig
chmod +x /tmp/rig
git clone https://github.com/<you>/infra ~/infra && cd ~/infra
/tmp/rig apply zephyr     # installs bun + rig itself as declared packages

The compiled binary embeds Bun, so the config's TS runs without Bun installed on the machine.

Internal architecture

Package layout

├── cli/           # arg parsing (util.parseArgs), renderers (pretty / ndjson)

Resource type contract

export interface ResourceType<Spec, Live, Meta = {}> {
  kind: string;                                  // "file", "pkg:pacman"
  scope(spec: Spec): "user" | "system";
  id(spec: Spec): string;
  merge?(a: Spec, b: Spec): Spec | Conflict;
  edges?(spec: Spec): string[];                   // implicit dependencies

  read(ids: string[], x: Executor): Promise<Map<string, Live | null>>;  // batched
  diff(spec: Spec, live: Live | null): Change | null;
  apply(changes: Change[], x: Executor): Promise<Result<Meta>[]>;           // batched
  destroy?(id: string, meta: Meta, x: Executor): Promise<Result>;
}
  • Batched read/apply is the key performance decision: one pacman -Qqe for 300 packages, one systemctl show for all units.
  • Executor abstracts run(argv), readFile, writeFile, stat. Local uses Bun.spawn / Bun.file / Bun.write; Privileged forwards to the helper; Fake records calls.
  • Hashing via Bun.hash.xxHash3 for change detection, SHA-256 for the object store.
  • Plugins: a user repo can export extra ResourceTypes from rig.config.ts — they're plain TS objects, so custom types are first-class.

Why Bun specifically

  • Runs .ts directly — config needs no build step, and bun check is just an editor/CI concern.
  • bun build --compile → single static-ish binary per arch; perfect for bootstrap and remote push.
  • Bun.$ for ergonomic, safely-escaped shell in exec guards; Bun.spawn for everything else.
  • Fast startup (~20–40 ms) keeps rig dot snappy.

Testing

  • Unit: bun test with FakeExecutor — each resource type has table tests (spec × live → change → expected argv).
  • Integration: podman containers archlinux:latest (plus CachyOS repo added) and debian:trixie with systemd as PID 1. Test suite applies sample configs, asserts idempotency (second plan is empty) and pruning (remove module → plan destroys exactly its resources).
  • User config CI: rig plan --offline --facts fixtures/zephyr.json evaluates and validates without touching a machine — catches type errors, conflicts and unknown package names (checked against a cached sync db).
  • Golden plans: snapshot test of plan output for the example repo.

Open questions

  1. Name. rig is short but may collide with existing binaries; check AUR/crates before publishing.
  2. Async modules? Allowing await in modules (e.g. fetch a key from a URL) is convenient but makes evaluation non-pure. Proposal: allow, but cache results in .rig/ and require --refresh to re-fetch.
  3. KDE settings granularity. Per-key kconfig is precise but verbose; a “capture current Plasma settings into a module” command may be worth it.
  4. Multiple users per host. Design assumes one primary user; home-scoped resources for other users would need per-user helpers.
  5. Pull mode. A systemd timer running rig apply --from git on the server would make it self-healing; out of scope for v1 but the bundle format should allow it.
